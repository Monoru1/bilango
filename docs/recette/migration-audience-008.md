# Préparer la migration 008 en recette

La base cible est `gobilan-recette` (PostgreSQL 17, Francfort). Au contrôle du 12 novembre 2026, le connecteur Render voit l’instance disponible mais refuse la requête SQL parce que la liste d’IP externes est vide. Le schéma hébergé et la présence d’une copie hors hôte restent à attester depuis un environnement privé autorisé.

1. Depuis un runner privé approuvé qui reçoit `DATABASE_URL` par le gestionnaire de secrets, exécuter à la racine du dépôt `node --import tsx apps/api/src/migrate-render-recette.ts --inspect` avec le code candidat qui contient 008. L’inspection s’exécute en lecture seule. Conserver la liste des migrations et des compteurs sans données utilisateur. Exiger que l’unique fichier en attente soit `008_audience_events.sql` avant toute demande d’autorisation limitée à ce fichier.
2. Faire approuver la destination hors hôte et le certificat public RSA de restauration. Depuis le même réseau privé, produire un dump PostgreSQL complet au format custom, dans un répertoire privé. Vérifier l’archive avec `pg_restore --list`, puis utiliser `scripts/encrypt-backup-export.sh` avec l’empreinte du certificat obtenue par un canal distinct.
3. Calculer l’empreinte SHA-256 du fichier chiffré, transférer uniquement ce fichier sur la destination approuvée, le relire et comparer les empreintes. Déchiffrer puis restaurer dans une nouvelle base isolée, sans fournisseurs sortants ni ordonnanceur. Contrôler les migrations, les contraintes, les comptes de lignes et les déclencheurs d’audit. Consigner l’identifiant d’archive, le test de restauration, sa durée et l’emplacement approuvé.
4. Sur la restauration isolée, valider le passage de 007 à 008 avec la garde en refus par défaut. Après approbation nominative de `008_audience_events.sql`, utiliser `RECETTE_MIGRATION_APPROVED_UP_TO=008_audience_events.sql` dans le contexte autorisé. Recontrôler la liste des migrations et retirer cette approbation temporaire. Laisser les deux drapeaux d’audience désactivés tant que les règles de confidentialité et de conservation restent ouvertes.
5. Si le nouveau code présente une régression, arrêter la collecte et revenir au code précédent par un changement Git approuvé. 008 ajoute des tables indépendantes. Une restauration de données reste une opération distincte à approuver après évaluation des écritures intervenues depuis le dump.

Le job PostgreSQL du candidat 008 restaure un dump de l’état 007, prouve le refus sans approbation, puis applique 008 sur cette copie jetable avec le nom exact. Il vérifie les données métier conservées, les tables d’audience vides et le redémarrage sans nouvelle écriture. Une sauvegarde chiffrée et restaurable de la base hébergée doit encore être produite et vérifiée sur la destination autorisée.
